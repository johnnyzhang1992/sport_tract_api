# 管理端「运动计划」数据页设计（docs/22）

日期：2026-11-18　状态：已实现（纯只读统计）

## 第〇节 · 口径拍板

| 口径 | 结论 |
|---|---|
| 周期 | 一律 `period='daily'`（周计划 2026-11-14 下线，存量周快照不进任何指标） |
| 渗透率分母 | **近 30 天有 finished 运动的去重用户**。曾建计划是全历史口径，与它直接相除会 >100%（历史用户流失后溢出），故分子分母必须同窗口：`近 30 天活跃 ∩ 建过计划 ÷ 近 30 天活跃` |
| 「建过计划」 | 现存计划文档 ∪ 有过 daily 快照的用户（后者覆盖「闲置取消删文档」的人） |
| 达成率 | 用周期快照（T-1 结算），`total=快照期数`、`achieved=allAchieved=true 的期数` |
| 「今日有运动」 | 实时聚合（现存计划用户里今天有 finished 运动的去重人数） |
| 新增计划趋势 | 按现存计划文档 `createdAt` 落桶——**已知近似**：闲置取消会删文档，历史不可回补；P1 上 `plan_events` 事件采集后修正。接口带 `newPlansNote` 下发给前端展示 |
| 完成率分档 | `minRatio` = 三项已设目标里最弱一项的完成比（与小程序 overStreak 同口径）；分档 `[<50%, 50–99%, 100–199%, ≥200%)` 左闭右开 |
| 目标档位 | 距离 `≤2km / 2–5km / 5–10km / >10km`、时长 `≤15 / 15–30 / 30–60 / >60 分钟`——**上限含等号**（3km 必须落 2–5km、2000m 必须落 ≤2km）；次数 `1 / 2 / ≥3 次` |

## API（全部 `adminAuth`，只读）

- `GET /admin/plans/overview`：汇总卡
- `GET /admin/plans/trend?days=7|30|90`：labels + 总/单项达成率 + newPlans（非法 days 回退 30）
- `GET /admin/plans/distribution`：目标档位（现存计划）+ 完成率分档（近 30 天快照）
- `GET /admin/plans/users?page&pageSize&status&distTier&sortBy&order`：用户计划列表
  - `status`: `active`（有计划文档）/ `cancelled`（无文档但有快照）
  - `distTier`: `t1~t4`（按距离档，只对 active 行有意义——cancelled 无计划文档，与档位组合必为空）
  - `sortBy`: `createdAt`（默认）/ `rate30` / `achieved` / `streak`；`order`: `asc|desc`（默认 desc）
- `GET /admin/plans/users/:id`：目标 + 近 3 个月逐日快照 + 汇总（`changed` 用 `updatedAt - createdAt > 60s` 近似「改过目标」）

实现：`services/admin-plan-stats.ts`（service 直调支持注入 `now`，测试用 FIXED_NOW 免受共享 dev 库污染）。

## 已知限制（P0 接受，触达阈值时再改造）

- `perUserSnapStats` 全量扫快照表 + 列表接口 JS 内存排序分页：建计划用户 ≤5k 前可接受；超过后改聚合 `$facet` 或落统计表
- `adminPlanUserDetail` 复用 `perUserSnapStats`（全站扫描只为取一人），量大时改为只查该用户
- 新增计划趋势在 P1 事件采集前偏低（见口径表）

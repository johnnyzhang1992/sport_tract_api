# 日志存储与查询（2026-11-19）

> 给维护者和其他 agent：查日志前先读这篇。日志分三层，位置和存活期完全不同，
> 用错地方会得出「没有日志」的错误结论（2026-11-18 查「昨天的登录失败」就踩过）。

## 三层日志一览

| 层 | 内容 | 位置 | 存活期 | 查法 |
|---|---|---|---|---|
| **① 应用日志** | 结构化 JSON（请求进出、业务 info/error，与 docker logs 内容相同） | **宿主机** `/data/history-docker/logs/sport-track-api/app.log`（容器内 `/app/logs/app.log`） | **跨部署永久**（单文件追加，无自动清理，见「留存策略」） | `ssh` 上服务器 grep/jq，或 `docker exec history-sport-track-api cat /app/logs/app.log` |
| **② 容器 stdout** | 与①完全相同的内容（pino 双写） | docker json-file（宿主机 `/var/lib/docker/containers/<id>/…-json.log`） | 单文件 50M × 3 个轮转；**容器删除即丢** | `docker logs history-sport-track-api`（`--since 2h` 等过滤） |
| **③ nginx 访问日志** | HTTP 访问记录（状态码/IP/URL，**无应用层错误信息**） | 容器内 `/var/log/nginx/host.access.log`（**未挂载宿主机**） | **随 nginx 容器重建丢失**（上次重建 11-11，运行中 10 天+） | `docker exec history-nginx` grep；`access.log` 软链到 `/dev/stdout` 那份走 `docker logs history-nginx` |

**查历史问题 → ①；看实时请求/状态码分布 → ②或③；查「昨天为什么 429/401」→ ①
（有应用层 message）+ ③（有来源 IP，但 nginx 重建后会丢）。**

## 应用日志（①）格式与查法

pino JSON 行，每行一个对象。常用字段：

```json
{"level":30,"time":1795022625056,"reqId":"req-1","req":{"method":"GET","url":"/…","remoteAddress":"1.2.3.4"},"res":{"statusCode":200},"responseTime":11.2,"msg":"request completed"}
```

- `time`：毫秒时间戳（东八区换算 `date -d @$(echo "t/1000" | bc)`）
- `level`：30=info，40=warn，50=error（查故障先 `grep '"level":50'`）
- `reqId`：同一请求的 req/completed 两行用它串联

常用命令（服务器上）：

```bash
# 今天所有登录失败（401/429 等）
grep "auth/login" /data/history-docker/logs/sport-track-api/app.log | grep -vE '"statusCode":200'

# 某个 reqId 的完整请求生命周期
grep "req-abcd" /data/history-docker/logs/sport-track-api/app.log

# 慢请求（>2s）
grep '"request completed"' /data/history-docker/logs/sport-track-api/app.log | grep -oE '"responseTime":[0-9.]+' | awk -F: '$2>2000'

# 所有 error
grep '"level":50' /data/history-docker/logs/sport-track-api/app.log
```

## 为什么是现在这个方案（演进记录）

| 阶段 | 方案 | 问题 |
|---|---|---|
| 2026-11-19 之前 | 仅 docker logs（json-file **无轮转**） | ① 无上限（雪泥项目某容器已涨到 104M）；② **部署 force-recreate 即丢**——2026-11-18 查「昨天的登录失败」时发现应用层日志已随容器消失，只剩 nginx 的状态码 |
| 2026-11-19 现在 | **双写**：pino.multistream 同时写 stdout（→json-file 轮转 50M×3）+ 宿主机 `app.log`（compose 挂载） | 覆盖了两个问题：轮转防膨胀，挂载防重建丢失 |

坑（已写入 `src/app.ts` 注释，勿再踩）：
1. **Fastify 5 的 `logger:` 选项只收配置对象**，裸 pino 实例必须走 `loggerInstance:`，
   否则启动即崩 `FST_ERR_LOG_INVALID_LOGGER_CONFIG`（生产崩过 40 分钟，靠服务器上
   的 dangling 旧镜像回滚恢复——这也是「prune 前留一个能跑的镜像」的理由）。
2. `loggerInstance` 会让 Fastify 泛型 logger 收窄，tsc 过不去 → 对 options 对象整体断言收口。
3. **测试全绿拦不住这类崩溃**：测试走 development 分支（pino-pretty），
   生产分支只有真在 `NODE_ENV=production` 下做启动冒烟才能验证。部署手册应加此步骤。

## 其它容器

- **nginx**：`access_log` 写容器内文件（未挂载），stdout 只有小部分。重建会丢访问记录。
  若需要长期留存访问日志，后续把 `/var/log/nginx` 挂到宿主机即可（未做，权衡：挂了会持续增长需要手动清）。
- **history-book-api（雪泥）**：用的是 `journald` 驱动 + `tag`，日志进 systemd journal——
  `journalctl CONTAINER_NAME=history-book-api` 可查，**跨容器重建留存**（已实测）。
  这是我们 docker 日志方案的备选替代（journald 自带持久+轮转），sport-track 未采用的原因：
  双写文件方案已满足需求，且文件 grep 比 journalctl 查询更顺手。
- **docker 全局轮转**：compose 里 `x-logging` 锚点（json-file 50M×3）已挂到全部 12 个服务，
  新增服务记得也挂 `logging: *default-logging`。

## 留存策略（人工，当前无自动清理）

- `app.log` 增速实测 ~13KB/10s 高峰、日均 <10MB，单文件一年 <4GB，磁盘 32G 空闲——暂不自动清理。
- 需要时手工归档/清理：`gzip /data/history-docker/logs/sport-track-api/app.log.$(date +%m)` 后重建同名文件（容器内进程持有句柄，`> app.log` 截断即可，无需重启）。
- 若未来量级上来（>100MB/日）：改 pino `transport: target: 'pino/file'` + `pino-roll` 按天切分 + cron 清 30 天前的。

# 方案：轨迹清洗引入 GPS 精度（accuracy）因子

> 状态：待评审 → 实施中
> 日期：2026-09-23
> 关联：`src/utils/trajectory-clean.ts`（漂移清洗）、`src/services/activity.ts`（finish/reprocess 管线）

## 1. 背景与问题

客户端每个轨迹点都上报 `accuracy`（GPS 水平精度圈半径，米），数据库已落库，但**纠偏/距离计算全程未使用**。

现有漂移清洗（`cleanTrajectory`）完全依赖行为特征：尖刺判定（短时高速+方向反转）、孤立离群判定（偏离前后连线）。这套规则对"跳出去又跳回来"的经典漂移有效，但存在盲区：

> **精度差的点可能连续多个往同一方向偏**——方向顺随运动、速度不异常，行为规则看不出来；
> 而点自身上报的 accuracy 已经明示"我可能偏几十米"，这个信息被浪费了。

后果：高楼/树荫环境下的慢速运动（散步/徒步）距离被悄悄注水，且注水幅度与 GPS 环境正相关。

## 2. 设计原则

1. **好精度零影响**：accuracy 达标（< 阈值）的点，清洗行为与现状完全一致——不误杀真实转弯；
2. **差精度加严**：accuracy 差的点，偏离容忍度放宽（更容易判漂移），且不再要求"高速+反转"双条件；
3. **旧数据兼容**：accuracy 缺失（老点/导入点）→ 走现行规则，行为不变；
4. **只影响清洗，不影响渲染**：被剔除的点从轨迹序列移除（与现有漂移点同待遇）。

## 3. 规则设计

### 3.1 阈值定义

| 常量 | 值 | 说明 |
|---|---|---|
| `ACC_GOOD_M` | 25m | 优于该值 = 好精度，走现行规则 |
| `ACC_BAD_M` | 50m | 差于该值 = 差精度，触发加严规则 |
| `ACC_OUTLIER_FACTOR` | 1.0 | 差精度点的离群判定：点到前后连线中点距离 > accuracy × 1.0 即判漂移 |

- 阈值依据：手机 GPS 在开阔地 accuracy 中位数约 5~15m；城市峡谷 20~40m；>50m 基本是半失锁状态。
- 25~50m 之间为灰色地带：不触发加严（避免大批量误杀），仍可被现行行为规则正常处理。

### 3.2 判定流程（在现有 cleanTrajectory 的孤立离群检测处加一条前置短路）

```
对每个待检点 p（非暂停点）：
  1. 现行行为规则判定（尖刺/离群）→ 命中则剔除（不变）
  2. 新增：p.accuracy != null 且 p.accuracy >= ACC_BAD_M
     且 p 与"前后有效点连线中点"的距离 > p.accuracy × ACC_OUTLIER_FACTOR
     → 直接剔除（跳过现有"速度/角度"双条件）
```

要点：
- **加严只作用于"位置本来就偏得离谱"的点**——偏移没有超过 accuracy 本身的差精度点仍保留（它们可能只是精度虚报，位置其实没错，杀了反而伤渲染）；
- 连续差精度点会被逐个处理（前一个被剔除后，后一个以前一个有效点为基准继续判），不会因"连片偏移"而漏杀；
- 尖刺（双向高速）规则保持原样——accuracy 只补充"孤立离群"这一类。

### 3.3 数据流改动

| 位置 | 改动 |
|---|---|
| `CleanTrackPoint` 接口 | 加 `accuracy?: number \| null` |
| `trajectory-clean.ts` | 常量 + 离群前置短路 |
| `activity.ts` 管线 | 组装 CleanTrackPoint 时透传 `trackPoints[].accuracy`（已入库，零成本） |
| 兼容性 | accuracy 缺失 → `p2.acc >= ACC_BAD_M` 恒 false → 行为与现状一致 |

## 4. 验证方案

1. **单元对照**（test/trajectory-clean.test.ts 追加）：
   - 好精度点离群 40m：行为与现状一致（现行规则说了算）；
   - 差精度点（acc=60）偏 40m：新规则剔除（现行规则会保留）；
   - 差精度点偏 30m（< acc×factor）：保留；
   - 无 accuracy 的点：行为与现状完全一致；
2. **真实数据前后对比**：从 dev 库取全部 finished 轨迹，逐条跑 旧管线 vs 新管线，输出：
   - 每条：原始距离 / 旧清洗后距离 / 新清洗后距离 / 差异比例 / 被新规则剔除的点数及其 accuracy 分布；
   - 预期：绝大多数轨迹零变化；有变化的集中在 accuracy 差的点密集的轨迹（城市峡谷环境），距离小幅下降。

## 5. 真实数据对比结果（2026-09-23，dev 库）

- 样本：1360 条 finished 轨迹，50,232 个轨迹点
- 点级 accuracy 分布：**null 97.4%**（48,917 个，accuracy 字段上线前的历史点）、10-25m 2.6%（1,314 个）、25-50m 仅 1 个、**≥50m 为 0 个**
- 新旧管线对比：**0 条轨迹受影响**——库内不存在 acc ≥ 50 的点，新规则零触发
- 结论：
  1. 近期客户端上报的点精度全部落在 10-25m（质量好），当前数据无注水问题；
  2. 新规则作为"保险丝"上线零风险（对现有数据零改变），只在恶劣 GPS 环境（隧道/高楼峡谷，acc ≥ 50）时兜底；
  3. 97.4% 的 null 说明 accuracy 上报是近期才加的——随着新数据积累，该规则的覆盖面自然扩大。
- 对比脚本：`scripts/compare-accuracy-clean.mjs`（只读，可随时重跑）

## 6. 坐标存储紧凑化（2026-09-27 追加实施）

**格式（v2）**：finish/auto-finish/reprocess/import 落库的 trackPoints 改为——
- lat/lng 保留 7 位小数（≈1.1cm，抹平平滑算法的 15 位浮点伪影）
- timestamp 字段名不变，存相对 startTime 的毫秒数（识别：>1e12 为旧格式绝对 ms）
- pauseGap/still/vehicle 稀疏存储（仅 true 写入）
- speed/altitude/accuracy/seq 保留

**关键原则——先紧凑化、再算指标**：finish/auto-finish/reprocess/import 的执行顺序统一为
`管线 → compactTrackPoints → calcStats/calcFastestKm → 落库`，
保证落库指标永远 = 基于落库点重算的值（bestRecords 惰性补算与存储自洽）。
教训：先算指标再紧凑化，7 位舍入的 ±0.006m 抖动会让 1km 分段完成点偏移，
惰性重算出不同的 fastestKm（合成轨迹上 200 → 283 s/km）。

**读兼容**：`normalizeTrackPoints` 将库内任意格式归一为绝对时间戳 + 全字段旧形状，
DTO 下游（详情渲染/回放/GPX 导出经 absTs 修正）零感知。旧数据不迁移、读时动态兼容。

**收益**：每点 JSON 194B → 约 135B（-30%）；speed 保留（用户决策）。

- 回滚 = 还原清洗函数（无持久化副作用）。

## 8. 采样断档连线标记 gapJump（2026-09-27 追加实施）

**要解决的问题**：丢锁几秒后重定位，位置一步跳到人不可能到的地方，地图上画出一条不该存在的直线
（线上样本 `6ab8f4d7d5b8a92521664bc7`，593 点里 5 次单步 66–112m / 6–10s，而全程中位步速只有 2.33 m/s）。
**注意**：这条样本的 5 处后来量出来是「沿跑道把弯切了」（与行进方向夹角 1–11°），不是横穿，所以它现在
一处都不该断线；本标记只针对位置横向跳出走廊的那类。两件事都记在这里，是因为判据的第三条就是被这条
反馈逼出来的。

**为什么前三条路都不通**（都实测过，别重走）：
1. 速度阈值：漂移步的「进入步」快得离谱、「离开步」却是正常速度，规则要求双向都超 → 结构上永远卡在这半边；
   且自适应门槛取「局部中位 × N」，连续漂移会把局部中位本身抬到 5–12 m/s，实测门槛被顶到 20–46 m/s，
   类型下限那一项永不生效。
2. 精度因子（本文件 3.x）：漂移点自报精度常常是 5m，反而比邻居（15/28m）更好——先兆在**前一步**，不在本点。
3. 删点：删掉落点后前后两点直连，弦只是换个长度（75m/7s + 15m/3s → 60m/10s），斜穿照样斜穿。
   **弦是「时间间隔」的属性，不是「某个坏点」的属性。**

**判据**（`src/utils/track-gap.ts`，与运动类型无关，靠全轨迹中位数自适应，三条同时成立才标）：
1. 间隔 `≥ max(2×中位间隔, 5s)`；
2. 位移 `> max(25m, 中位步速 × 间隔 × 2.5)`；
3. **横向偏移** `> max(20m, 中位步速 × 间隔 × 1.5)`——横向 = 这一步位移在「断档前 6s 弦」与「断档后 6s 弦」里
   更贴合那条上的垂直分量；两侧任意一侧取不到参照就不判。
2.5 倍余量的依据：实测漂移步是中位步速的 4.5–5.1 倍，真冲刺/加速到不了 2.5 倍；
用全轨迹中位（不是局部窗口）当基准，因为中位数天然抗离群，且它就是这次运动自己的节奏。

**第 3 条是踩了坑才加的**：只有前两条时，那条跑步样本（本地副本 591 点）判出 5 处，断开后用户反馈
「修正后的轨迹看着怪怪的」「看上去还不如原来」。逐条量过：那 5 步与局部行进方向夹角只有 **1–11°**
（横向偏移 1.3–12.6m），且沿线 15m 内分别还有 70–115 个别的轨迹点——它们是**沿着跑道把弯切了**，
线本来就贴着自己的轨迹，断开等于在正常的线上挖 5 个洞。用户最初说的「直角」来自切角
（7–10s 没采样，把 15–25m 的弯连成 75–112m 的弦），不来自横穿；切角不该断线。
参照窗口取 6s 而不是 10s、并且前后两条弦取小，都是为了让弯道上不误判（10s 的弦在跑圈时已偏出切线十几度）。

**已知盲区（写清楚，别当已解决）**：连着两次丢锁时，第二次的「断档前 6s」内没有参照点 → 不判、线照画；
起步第一步同理。取向是「拿不准就保留连线」，宁可少断不可挖洞。

**口径：只改视觉，一个数字都不动。** 标记打在「该步的落点」上，语义与 pauseGap 一致（渲染方遇标记点在此处断开连线）；
距离/配速/最快公里/卡路里/单段明细/配速区间统计一律不接这个标记（`test/track-pace.test.js` 有专门一条钉死
「splitByPauseGaps 不看 gapJump」，防止哪天把视觉口径漏进指标）。点不删、坐标与时间戳逐位不变。

**接线**：`finish` / 惰性收尾 / `reprocess` / `import` 四条写路径 + schema 字段 + 紧凑存储稀疏位（v2 沿用）+
`normalizeTrackPoints` 读归一 + `/overview`（投影 select、切段、段首重打标、缩略图补回）+ `/activities` 列表
（`gapPoints` 聚合并入 `previewPoints`）。渲染端：小程序 `utils/track-pace.js#splitByUnreliableLinks`
（track-map 三种着色模式、合集页 canvas、分享海报、卡片缩略图共用）；webAdmin `utils/pace.ts#lineBreakRanges`。

**验证**：api `npm test` 352 pass / 两条 typecheck 干净；miniapp `npm test` 309 pass；webAdmin `tsc -b && vite build` 干净。
每条用例都做过变异校验（去掉 select 字段 / 去掉 `$or` 过滤 / 去掉合并携带标记 / 去掉切段条件 /
去掉前端字段透传 / 去掉横向闸门 / 只用前方弦 / 只用后方弦 → 各自能复现对应的红）。
真实数据核对（本地 dev 库那条跑步，591 点）：三条判据下判出 **0 处**，坐标与时间戳逐位不变。
浏览器端在**同一投影**下量轨迹像素（轨迹 bbox 对角线 579.87px 两次完全一致）：
0 标记 = 25461 px（原样）↔ 人为去掉横向闸门让 5 处都断 = 22243 px（少的 3218 px 就是那 5 条线）。
小程序侧同样做过 A/B：同页 setData 开/关标记，2904 px 差异全部落在弦所在带内。

**待决**：
- 历史数据回填：现有点里没有这个标记，需要走 reprocess（或照 vehicle 那轮做一个管理端批量接口）；
- 距离折算：那 5 步画了 414m，按中位步速实际只能走约 86m，**距离虚高约 328m（占该条 3.244km 的 10%）**。
  用户已明确「这轮先不动」。注意折算不能复用这个视觉标记（第 3 条会把沿跑道的切角排除掉），
  要按前两条时间+位移判据另算一遍；
- 「首点跳」（起点 GPS 未收敛）仍是删除处理，未改标记。

## 9. 断档虚高影响评估接口（2026-09-28 追加，只读）

`POST /admin/activities/gap-impact`（管理端，**不写库**）：`{ ids?, userId?, limit?, listCap? }`。

**口径与视觉标记不同**：这里用 `detectGapSteps()`，只看前两条判据（间隔拉长 + 位移超限），
**不带第三条横向闸门** —— 因为"沿跑道把弯切了"的步视觉不该断线，可它的里程虚高是实打实的。
每条报：点数 / 距离 / 断档处数 / 弦长 / 应有 / 虚高 / 虚高占比 / 折算后距离 / 平均配速前后；
汇总给总里程前后、分桶（≤1% / 1–3% / 3–5% / 5–10% / >10%）与明细（按占比倒序、可封顶）。

**不伪造数字这条底线**：虚高 ≥ 整条里程 50%（`UNRELIABLE_OVER_PCT`）的行判为整条不可信 ——
点极少的烂轨迹里中位步速本身就是从漂移步取的，拿它折算是用鬼数换实测数。这类只标 `unreliable`、
`distanceAfter`/`avgPaceAfter` 给 null、不进分桶也不扣总里程。写它是因为第一版把它夹成了 1m，
算出"配速 540000 秒/公里"这种东西 —— 评估报告里出现一个假数，比不报更糟。

**只读承诺有测试兜着**：跑完比对整条文档（含 `updatedAt`，所以"值没变但被写过"也抓得住）。
变异校验：阈值顶到永不触发 / 压到全都不可折算 / 折算不扣虚高 / 服务里偷偷写一次库 —— 各自能复现对应的红。

**本地 dev 库跑出来的数（不能当线上看）**：1654 条 finished 里 4 条含断档共 11 处；
其中 1 条是 9 点 1200m 的测试垃圾数据（虚高 125.9%，判为不可折算）。
真实用户数据 3 条：`6ab9066c`（5 处 / 虚高 328m / 10.1%，3244→2916m，配速 6'07"→6'48"）、
`6ab8fd32`（同一场跑步的导出→导入副本，4 处 / 239m / 7.2%）、一条 walking（1 处 / 78m / 13.3%）。
可折算部分合计虚高 645m，占该库总里程 0.052%。
**线上影响面的实测见第 10 节**（用只读脚本直接从管理端 API 拉线上数据算，没等接口部署）。

## 10. 线上全量评估与判据候选对照（2026-09-28，结论：不改）

两条只读取证脚本（都在 gitignore 的 `scripts/` 下，token 只走环境变量）：
`gap-full-prod.ts all` 逐条 GET 线上 finished 算影响面；`gap-criteria-compare.ts` 把原始点一次性落到
`scripts/.cache/gap-prod-raw.json`，之后换判据只离线重算，不再要 token。样本：线上全部 **300 条** finished。

线上口径的数（当前判据 ①②③）：

- 18 条含断档 / 共 44 处；虚高合计 **3211m**，总里程 792279m → **0.405%**。虚高 >5% 的 10 条；
  虚高 ≥50% 判为不可折算的 4 条。
- 按类型：running 0.39%、walking 0.59%，hiking/cycling/mountaineering 共 16 条 **0 处**。
  差值小于单条之间的抖动，且与"散步里也可能比跑步快"这个事实一致 → **不设按运动类型的速度门槛**。
- 对照量：跨暂停位移合计 **11715m = 总里程 1.48%**（109 条带 `pauseGap`），比断档虚高大 3.6 倍。

判据候选只动第②条（"这一步算不算超出自己节奏"），①③ 保持。全库结果：

| 候选 | ②的写法 | 判出条数 | 处数 | 视觉处 | 虚高m | 占里程 |
|---|---|---|---|---|---|---|
| CUR | 全步中位步速 ×2.5 | 18 | 44 | 3 | 3211 | 0.405% |
| A1 | 基准剔掉"没在动"的步 | 8 | 21 | 1 | 1544 | 0.195% |
| A2 | 基准换成 p75 | 15 | 34 | 2 | 2513 | 0.317% |
| A3 | 基准剔掉 `still` 步 | 17 | 39 | 2 | 3211 | 0.405% |
| A4 | 基准换成 30s 窗口 pace 中位 | 17 | 40 | 2 | 2995 | 0.378% |
| B10 | 不设自身基准，只判 >10 m/s | 13 | 24 | 1 | 1882 | 0.238% |
| B20 | 只判 >20 m/s（对骑行也安全） | **0** | **0** | **0** | 0 | 0% |

三条决定性证据：

1. **B20 全库判出 0 处。** "完全不参考这条自己的节奏"和"能抓到现网这些跳变"不能兼得 —— 上限必须高到
   骑行（均速 10 m/s 很正常）不中招，就没有任何一步够格。B10 能用靠的是"只对步行/跑步生效"这个
   没说出口的假设，而它确实会误判 1 条骑行轨迹里的正常高速步。
2. **A1 比现状更差**，且原因与第 8 节开头记的纠偏失效是同一个坑、方向相反：把静止步剔掉之后，
   走走停停的轨迹里剩下的"在动的步"主要就是漂移步自己，于是**漂移把自己的基准抬上去了**
   （两条已知真跳变 `6aad109c` 11.96 m/s、`6ab8f4d7` 5 处 10.72–11.96 m/s 全部漏判）。
   A 族里只有 p70/p75 这档能同时修掉已知误伤、又保住真跳变；敏感性：p60 误伤回来，p90 开始漏真跳变。
3. **把①放开**（>10 m/s 的步不看间隔直接进池）全库多进 36 处（18 条，含 17.6 m/s 的"跑步"步），
   其中**过得了第③条横向闸门的 0 处** —— 它们全是沿轨迹向前蹦，线本来就贴着自己的轨迹。
